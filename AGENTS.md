# Étaye shared agent policy

Étaye supports consultation preparation, evidence inspection and clinician-reviewed documentation for isolated multi-practitioner practices. Start from docs/README.md and docs/continuation.md for the current Spring Boot, React TypeScript and PostgreSQL scope.

## Policy

- Implement only after the required design review and Aymen's written story authorization. Check `[etaye] authorized_stories` in `_bmad/custom/config.toml` and verify the scope and exceptions in the decision register. Leave the global `development_authorized` flag false.
- When asking Aymen to approve a design, architecture, scope or process decision, show a local HTML review page built with Étaye's actual tokens. Show the current and proposed states and give explicit choices. Record the scope of each approval. Distinguish design approval, story development authorization, running UI approval and merge authorization.
- Speak French with Aymen. Write repository documents, requirements, ADRs, stories, reports and handoffs in English. Use English technical identifiers/comments and Conventional Commits/PR text. Preserve Étaye and existing French interface copy; English demo language remains a product decision.
- User decisions govern scope. docs/planning-artifacts/business-rules.md owns domain behavior; prd/prd.md owns requirements; ADRs own technical choices; verified Figma properties own existing visual values. Surface conflicts explicitly; a newer file or previous AI answer is not automatic authority. Distinguish User decision, Verified observation, Proposal, [ASSUMPTION] and To verify.
- Legacy source is read-only reference; inspect its actual current commit when needed. Never copy professional reference content, infrastructure, URLs, credentials or business rules into Étaye. Use GitHub, not organizational GitLab procedures.
- Use exclusively synthetic people/data in demo, tests, documents and screenshots. Claim no clinical validation, certification, regulatory compliance or real patient readiness without established evidence.
- Request relevant missing access promptly after checking existing connector/CLI capabilities. Distinguish credential, permission, subscription and unsupported capability; give minimum scope, current official steps and safe configuration location. Verify minimally. Never commit/log/display secrets; never activate paid services or expand permissions silently.

Record consulted source versions/dates, assumptions and effects on acceptance criteria. A summary or older story is insufficient.

- Before future implementation, additionally verify the development authorization, approved exact Figma nodes/tokens, design coverage/exceptions and current implementation tracking. Read the whole story and relevant ADRs; do not infer completion from file existence.

Test strategy/evidence: docs/test-artifacts/. Record deferred scope, rationale, dependencies, impact and resumption trigger in docs/planning-artifacts/deferred-work.md. ## Running and verifying

- Before each BMAD workflow, resolve effective core and module config with `uv run --no-cache _bmad/scripts/resolve_config.py --project-root "$PWD" --key core` and `--key modules.bmm`; also run the workflow's resolve_customization.py invocation. Respect team/personal override layers; do not rely only on generated YAML/defaults. Paths containing {project-root} expand once.
- Node20.12+, Python3.10+ and uv are BMAD prerequisites. See docs/agent-setup.md for the installed tools and docs/implementation-artifacts/ for executed verification.
  - API (Java 25, Maven wrapper; Docker is required because tests use Testcontainers): `cd apps/api && ./mvnw -B -ntp verify`. It also enforces the build environment, production warnings as errors outside two tracked categories, and the coverage floors. The compiler-debt profile checks the recorded serial and deprecation warnings in production and test sources.
  - Web (Node 26, pnpm 12.21.0 through Corepack, which Node 26 no longer bundles: `bash tools/install_corepack.sh` once, which verifies the release digest): `corepack pnpm install --frozen-lockfile`, then in `apps/web` `corepack pnpm verify` (lint, SDK drift, types, unit tests with coverage floors), `corepack pnpm build` and `corepack pnpm test:smoke` (stubbed probe). The real outage spec `ETAYE_E2E_DB_CONTAINER=<compose container> corepack pnpm test:e2e-real` needs the real stack and stops and pauses its database.
  - Every gate, its failure condition and the pre-pull-request commands: [verification gates and local commands](docs/operations/cicd-deployment-strategy.md#verification-gates-and-local-commands). A pull request must run at least 80 % of the executable lines it changes in API production code and Web logic modules (`.ts`), and no changed file of ten or more such lines may fall under 50 %; the page and component files (`.tsx`) have no line measure. Never lower a coverage floor, add a lint suppression or exclude a compiler warning category to pass a build; the only exceptions are the bounded debt baselines of the deferred register (D-67 for lint, D-68 for the compiler), which can only shrink. Remove the corresponding diagnostic entries when fixing debt. For ESLint also prune the bulk-suppression counts.
  - Local database: `infra/local/docker-compose.yml` needs the four generated passwords documented in the implementation record; `infra/local/verify-init-roles.sh` exercises the provisioning script in throwaway containers.
  - GitHub requires `API verify` and `Web verify` on `main` (UD-47, D-40). Both jobs start for every pull request and run the application suites on relevant changes. Cite an actual run and its executed steps when reporting test evidence.
- For this package run `python3 tools/validate_docs.py`; it checks documentary links/references/invariants, not application behavior. Never report documentary checks as passing application tests.

## Domain and architecture constraints

- Enforce current server-side capability plus practice/record ownership on every query/write/job/source/file/export. A route practiceId, frontend filter or stale session claim is not authorization. Administrator does not imply clinical access; portal identity links are explicit and record-local.
- Separate appointment, consultation, document review, task processing, freshness and publication states. Missing data is not normal data. Validation never automatically publishes. Clinician briefs are not patient explanations and cannot be directly published.
- Preserve source facts, generated baseline, human edits, immutable approved versions and dated citation lineage. Review that citations actually support claims. Source changes mark relevant content stale; regeneration cannot silently overwrite corrections. Publish/replace/withdraw only with exact-version/audience guards.
- Follow the modular-monolith ADRs and data/API boundaries. Transactions own RLS context, concurrency checks, audit and outbox integrity; background/external work uses scoped bounded jobs. Applied migrations remain immutable when implementation begins. Do not add brokers/microservices/vector storage without a documented need.
- Treat uploaded/record text and provider output as untrusted data. Minimize outbound data, keep deterministic AI at the external provider boundary for demo/CI, and never describe filtering/pseudonymization as guaranteed anonymity.

## Visual and delivery requirements

- Before future UI work inspect exact current Figma nodes/properties/screenshots/comments and record refs; reuse original logo/tokens. For missing designs finish and review them first, unless Aymen explicitly accepts a named exception. Do not estimate existing tokens or inherit a generic component theme.
- If Figma cannot be read (quota, access, no Desktop), work from docs/design/design-system.md and its linked sources, record the limit and what stayed unverified, and reconcile with Figma later; never estimate tokens or treat that file as design approval. Aymen's 2026-11-18 decision is that the mockups must be implementable without Figma; the exception record and its limits are in section 14 of that file, and it neither authorizes development nor replaces design approval.
- Preserve Étaye’s visual identity across every UI story and state. Apply the [page-state continuity rule](docs/design/design-system.md#continuity-across-page-states) in design, implementation and review. Record the approved shell and background in the context packet and verify both in opened light and dark comparisons.
- Open actual running-UI screenshots and compare at matching desktop/tablet/mobile viewports, including long/empty/error/restricted/focus states. Record the family, state, viewport, theme, tested revision and evidence links for the comparisons actually opened. Open all PDF pages and review email layouts. Functional tests/builds and visual fidelity are separate evidence requirements.
- Test critical journeys on an isolated real Spring/React/PostgreSQL/file stack, deterministic only at external AI/email/scan boundaries where appropriate. Required suites must execute with meaningful assertions; a zero-test success is failure. Preserve real evidence/limits.
- Future feature work uses short-lived feat/<story-id>-<slug> or fix/<story-id>-<slug> branches and PRs to main, never feature development directly on main. docs/<slug> is valid for documentation. When finalizing a story on GitHub, follow docs/operations/delivery-rules.md for the local review, mandatory manual CodeRabbit request and required checks.
- Before editing, inspect `git status` and `git worktree list`. For parallel agent work, use a dedicated worktree from the verified base and preserve other agents' changes.
- Before delivery review silent failures, edge cases and acceptance-criteria compliance, plus visual fidelity. Promote validated artifacts with traceable versions; never invent CI/coverage/deploy results.
- After a confirmed merge, fetch `origin/main` and verify each secondary worktree's integration, including squash merges. Remove clean, integrated local worktrees and their local branches. Preserve unmerged work and local modifications. Return the principal checkout to `main`, fast-forward it to `origin/main` and verify the checkout is clean and both refs match. Check the local cockpit at `../etaye-cockpit-suivi/Etaye-Ordre-US-Suivi.html` against the confirmed merge. If it is stale, follow that repository's README to regenerate it from the updated checkout and verify the rendered story status and PR number.
- Commits are coherent English Conventional Commits without emoji, added Co-Authored-By trailers or automatic attribution text. Preserve third-party licenses and credits in appropriate files. Comments explain a constraint or reason, not obvious code.
- Before yielding record phase, completed artifacts, open choices/access, actual verification and next action in docs/continuation.md. Read it on resume, then verify current Git/files rather than treating it as proof of completion.
