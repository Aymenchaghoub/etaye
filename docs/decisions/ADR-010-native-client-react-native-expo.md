# ADR-010 — Native client: React Native with Expo, distributed as a demo

Status: Accepted by Aymen on 2026-11-19 (UD-38, UD-39). Date: 2026-11-19. Amended 2026-11-20 by [ADR-014](ADR-014-design-system-closure.md) (point 7 below, the verified SDK 58 React version in point 2 and the DF-19 wording in the consequences; the choice is unchanged). Supersedes UD-14 for the shell technology, ADR-008 point 5 (packaging ladder) and the React Native alternative rejected in ADR-008. Related: UD-12, UD-13, UD-15, ADR-002, ADR-008, ADR-009, NFR-15, stories 10.2 and 10.4 to 10.8, D-15.

Aymen wants the portfolio to show three skills, an API, a web application and a mobile application (2026-11-19), and does not intend to publish the mobile apps: they are demos. The demos must show fluid, modern screens on a phone that call the real API, with a visual identity consistent between the web and mobile apps, and they must show command of the technologies and of the architecture (Aymen, 2026-11-19). A Capacitor shell is the web application in a webview, so it shows no mobile skill, and its main risk, the store review of a repackaged website (App Review Guideline 4.2), no longer applies without a store. The session, privacy and compatibility rules of ADR-008 and ADR-009 do not depend on the shell technology and stand, except where this ADR changes them.

**Choice:**

1. **Technology.** The native client is a React Native app built with Expo, in TypeScript strict, in a future `apps/mobile` beside `apps/api` and `apps/web`. Android comes first (increment 3); iOS follows the gate of story 10.8. Exact Expo SDK, React Native and React versions are locked at the spike. **Verified observation (2026-11-19):** the latest stable line is Expo SDK 58 with React Native 0.88 (released 2026-10-15). The audience stays the patient first (UD-13); practitioners use the responsive and installed web app, and D-16 stays deferred.
2. **What is shared.** The web and native apps share TypeScript packages that do not import React: the client generated from the OpenAPI contract (ADR-009), the output of the token bridge (a TypeScript token module for the native target, produced in story 10.6), domain types and platform-neutral validation or formatting helpers. They do not share UI components: native screens use React Native components and native navigation. **Visual identity:** one token source feeds both the CSS of the web app and the native token module, the same fonts (Atkinson Hyperlegible Next and Mono, Source Serif 4, loaded in the app) and the original logos are used, and the light and dark themes follow the device setting; native screens adapt layout, navigation and gestures, not identity. DESIGN.md still governs: restrained motion without gratuitous animation, and reduced motion respected. An Expo SDK pins its own React (19.2.x for SDK 56 and 57, 19.3.0 for SDK 58: verified 2026-11-20 in the bundled versions of `expo` 58.0.26) while the web proposal is React 19.3 (ADR-002), so the two apps may run different React versions.
3. **Session transport.** ADR-008 points 1 to 3 and 6 to 8 stand with one change: a React Native client is not a browser and has no origin. The issuance of the native session no longer relies on an allowlisted native origin. `createNativeSession` requires full credential verification, a declared client kind in `X-Client-Version` (ADR-009; a declaration, never proof) and a device registration. A request in bearer mode that carries a cookie, an `Origin` header or a `Sec-Fetch-Site` header is refused, which keeps "bearer is never accepted from a web origin". The CORS allowlist (ADR-008 point 4) covers browser origins only and has no native entry. The exact distinguishing headers are a spike check. The secret lives only in `expo-secure-store`. **Verified observation:** it uses the iOS Keychain and, on Android, SharedPreferences encrypted with the Android Keystore; an iOS Keychain item survives an uninstall when the app is reinstalled with the same bundle ID. The app therefore keeps a first-launch marker outside secure storage and wipes the secret when the marker is absent; server-side revocation covers the remaining gap.
4. **No clinical data at rest (UD-15, stands).** Clinical content is kept in memory only: no clinical payload goes to AsyncStorage, files, SQLite, logs or crash reports. A PDF to share or download is written to the app cache only while the system share sheet runs and is deleted afterwards; a copy the user saves elsewhere is outside the app's control, like a browser download (BR-013, BR-016). Clinical content is rendered with native components; no webview shows remote or clinical content.
5. **Distribution is demo-only (UD-39).** No store submission, no Apple or Google developer account, no store credential. D-15 becomes Not planned. **Verified observations (Expo documentation, read 2026-11-19):**
   - Android: Linux is a supported host for a local Android development build, and an emulator runs on it. A physical Android device can receive a package file.
   - iOS: Linux supports neither the iOS Simulator nor an iPhone build; every iPhone build needs a paid Apple Developer account for signing, and the current Expo guide for a physical iPhone with Expo Go also requires an active Apple Developer Program subscription (page modified 2026-08-17). The Simulator needs macOS.
   - Push: remote push notifications are unavailable in Expo Go on Android since SDK 53 and need a development build; an Android credential (FCM) is needed (cost To verify).

   Consequences for demos: Android is demonstrated on an emulator or a sideloaded package. The free iOS path is the installed web app (Safari, Add to Home Screen, Web Push from iOS 16.4, ADR-008 point 7). A native iOS demonstration waits for a Mac (simulator) or for Aymen's decision on the Apple program, taken at the story 10.8 gate. Native iOS push needs APNs and the Apple program, so it is outside the demo scope. **Real API on a real phone:** the native app always calls the real Spring API, never a mock; only the AI, email and scan boundaries stay deterministic, as for the web. A claim about fluidity or a real-device demonstration needs a physical Android phone (a package file or a development build over USB, both free); frame timing is recorded with device, build and scenario, and no target value is set before a baseline exists. Recorded demos from an emulator or simulator say so; they are not real-device evidence (NFR-15).
6. **Tests.** Unit and component tests with the Expo Jest preset and React Native Testing Library; a smoke journey on an Android emulator with a tool chosen at the spike (Maestro and Detox are candidates, To verify). The contract-drift check of ADR-009 covers the generated client.
7. **Execution precisions (amendment of 2026-11-20, ADR-014).** They refine the choice without changing it. (a) Fonts for the native app come as TTF or OTF files from the official SIL OFL distributions; the received WOFF2 files serve the web. The Expo font documentation shows only `.ttf` and `.otf` and does not say that WOFF2 is refused: **to verify** at the spike (D-51). (b) Icons use `lucide-react-native` with `react-native-svg` (SDK 58 bundles 15.16.0). (c) The light and dark themes use `useColorScheme` and the generated token module, with no styling library. (d) Reanimated (~4.7.1 in SDK 58) only if a motion pattern of ADR-012 is ported, with its static equivalent. (e) A TalkBack pass per screen is part of the definition of done. No native component library is adopted: the compatibility of the candidates with SDK 58 is not established ([review record](../design/reviews/2026-11-20-design-system-review.md)).

**Alternatives:**

- Capacitor shell (UD-14): rejected; no mobile skill is shown and its store argument is gone. Returning to it needs a new ADR.
- Flutter, Kotlin Multiplatform, or Swift and Kotlin natively: rejected; Dart or two code bases, no TypeScript reuse, and iOS needs a Mac in every case.
- Expo Go as the standard demo route: not retained; no remote push on Android and a paid program on a physical iPhone.

**Consequences:** UD-14 superseded and ADR-008 amended. Stories 10.2, 10.5 to 10.8 reworded with AT-039, AT-042 to AT-045. ADR-002 gains a native row, AD-11 and the glossary replace "native shell" with "native app". D-15 not planned; roadmap O-9 closed. Design follow-up DF-19: the native screens start from the received 390×844 designs of the patient families (pending Aymen's approval), with safe areas, navigation, permission copy, app icon, splash and a native answer for the background layer (CSS, not portable). The AGENTS.md design gate still applies: native screens are designed and reviewed before story 10.6 builds them. A second client adds UI test surface. Spike checks, not blocking acceptance: the bearer-versus-browser header rule, React version alignment in the workspace, FCM cost, the exact SDK lock and the license files of React Native and Expo (expected MIT). No account, credential or paid service is requested by this ADR.
