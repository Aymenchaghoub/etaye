# Future GitHub delivery rules

Status: Delivery policy. Development authorization is granted per story. Repository owner Aymen Chaghoub. Target `main`, no permanent integration branch. Use `gh` or the GitHub connector, never organizational GitLab tooling.

Use short-lived `feat/<story-id>-<slug>`, `fix/<story-id>-<slug>` and `docs/<slug>` branches. Initial tooling bootstrap is on main; planning package uses docs/planning-package. Do not develop features directly on main. Before story creation/edit/review read current relevant PRD/rules/epic/UX/architecture/data/API/AI/security/test/deferred documents and dependency stories; record sources/date/version, assumptions and effect on AC. Planning backlog becomes implementation-ready only after complete design review (or explicit specific exception), Aymen's development authorization and installed BMAD readiness gate.

Before assigning a future implementation story, prepare a focused context packet: story ID and objective, exact current source versions, linked requirements/rules, applicable ADR/data/API sections, approved Figma nodes/tokens and required acceptance/visual evidence. Use docs/README.md and traceability to find relevant authorities; read those current documents in full as AGENTS.md requires. Do not paste the entire docs tree or raw Figma snapshot into an agent prompt. If relevant context no longer fits, split the work or continue with explicit source references and notes; never substitute an old summary for a required current document. For a visible change, include the approved shell and background reference and its state comparisons under the [page-state continuity rule](../design/design-system.md#continuity-across-page-states). A packet does not grant development authorization.

Group coherent English Conventional Commits. No emoji, added Co-Authored-By trailer or automatic attribution text. Retain third-party licenses/credits in files. English PR title/body lead with trigger/problem and resulting behavior, validation evidence and material limits; no fake completed features. Keep story-related docs/tracking/report changes together where practical.

Before delivery: checks appropriate to change, critical real-stack isolated tests, three-lens review (silent failures, edge cases, acceptance criteria), running-UI comparison against exact Figma references/viewport, PDF/email review as applicable. Open PR to main, require actual supported checks/review, verify exact head before merge. When a change shows anything visible (a screen, a PDF, an e-mail, a smoke page), the reviewing agent also starts the application locally, opens the real result and tells Aymen what to check and how to run it; the merge waits for his reply (Aymen, 2026-11-19). Do not claim branch protection/CI as enabled until configured and observed. Documentation-only PRs use documentary checks, not fabricated application results.

Run one local **Zcode** review per implementation story (Aymen, 2026-11-21, UD-53). Attach the complete diff, current story and test evidence, with the exact revision. Invoke the headless prompt in an isolated directory with execution, editing and delegation tools disabled. Zcode 0.17.1 rejects headless `--mode plan` despite listing it in help. Use `zcode --mode guarded --prompt` on that version and restrict the available tools with `--disallowed-tools`, `--workflow-mode disabled` and `--toolsearch-mode off`. Ask for one report with three sections covering silent failures, edge cases and acceptance-criteria compliance. The implementing agent verifies and triages each finding, fixes confirmed issues and reruns affected checks. Record the reviewed revision, outcome and any access limit in the implementation record. **Tool update (Aymen, 2026-11-21, recorded with UD-56 for story 9.1):** from story 9.1 the end-of-story three-lens review runs once with the **Codex CLI** in read-only mode (`codex exec --sandbox read-only --skip-git-repo-check -C <repo> "<prompt>"`), never with subagents and never more than once per story; the Zcode invocation above remains the recorded method for the stories 1.2–1.3.

In review reports, cite the code or executed check that supports each verified finding. For conclusions that depend on an environment or configuration you could not inspect, record the limitation and the evidence needed to confirm them.

When finalizing every implementation story, explicitly request a CodeRabbit review on its GitHub PR, including draft PRs. Once the story diff and local review fixes are pushed, post `@coderabbitai full review` or use CodeRabbit's manual review control. If Aymen already requested the review for that revision, use the existing request. Verify that CodeRabbit acknowledged it or started the review, then triage the findings before merge. [CodeRabbit manual review commands](https://kb.coderabbit.ai/articles/1442026547-troubleshoot-why-coderabbit-reviews-might-not-trigger)

After a safe merge, verify the branch's work is integrated before deleting local/remote merged branches. Preserve unmerged commits/worktrees; never routine-delete unmerged work. Do not force-push or rewrite unrelated history. Keep actual progress in workflow tracking + stories/code/history/evidence and design coverage separately. Continuation note records phase, completed files, decisions/access/verification and next action.
