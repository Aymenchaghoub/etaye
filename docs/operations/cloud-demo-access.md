# Cloud demo access and custom HTTPS domain

## Live baseline and prepared change

**Verified observation, 2026-11-28.** Container Apps serves `8ea8b9826685` in Single revision mode. The app uses its generated Azure hostname, redirects HTTP to HTTPS with `301` and has one inbound Allow rule for the operator's IPv4 `/32`. HTTPS reaches only Nginx on port 8081. The platform readiness probe uses 8082 inside the replica. Spring Boot listens on loopback and reaches the existing Neon database over verified TLS. There is no additional ingress port or custom-domain binding. From the operator network, an unauthenticated HTTPS request to either `/connexion` or `/api/v1/session` returns `401` with the `Etaye Demo` Basic challenge. Neither challenge response included an HSTS header. The challenge comes from Nginx and is independent of the Spring session. The signed publication for `016d99a7e8f0` is a registry release. The latest protected workflow verified federated access in read-only mode. [Published release](https://github.com/Aymenchaghoub/etaye/actions/runs/46142317544) · [Read-only verification](https://github.com/Aymenchaghoub/etaye/actions/runs/46031644684)

| | Request path |
| --- | --- |
| Live baseline | Visitor → Azure HTTPS and operator IP allowlist → Nginx Basic challenge → Étaye sign-in → Spring authorization |
| Prepared private profile | Visitor → Azure HTTPS and the same operator IP allowlist → Nginx → Étaye sign-in → Spring authorization |

[The runtime template](../../infra/azure/app.bicep) defaults to `edgeAuthMode=basic`. Select `ip-restricted` explicitly for the target profile. Nginx refuses unknown modes and invalid hostnames at startup. In Basic mode it requires the visitor hash file. The hash remains in its existing Azure secret and is available for rollback. The generated hostname and any configured alias use the same host policy, proxy, operation restrictions and Azure ingress rule. Unrecognized HTTP hosts receive `421` if they reach Nginx. Both origins use the same HTTPS-only app and origins are configured by exact value. There is no added backend ingress or service.

**Verified observation.** The existing Neon project has public connections enabled and an empty database IP allowlist. A PostgreSQL TLS negotiation reached the direct endpoint from the operator workstation. The check supplied no database credentials. Neon access is protected by the existing authentication, verified TLS on the app connection, scoped roles and row-level security. Azure's web ingress policy does not cover the provider's database endpoint. The preparation adds no database route or change. A requirement for network-isolated PostgreSQL would need a separate provider and cost decision.

The browser sends the edge Basic credential in the HTTP Authorization header. Nginx strips that header before forwarding requests. Spring's browser session uses its own host-only cookie and CSRF token. In Basic mode a client or test must pass both gates and distinguish the two possible `401` responses. A native Bearer token would also be stripped. The private profile removes the Basic prompt on the approved network. It retains the current browser API and its restrictions. Native access still depends on the versioned mobile and token requirements. An installed PWA also needs separate validation of its manifest, start and offline routes and cache policy. Switching host creates a new browser origin, with separate installation, storage and cookies. Users sign in again on the new host. Azure's free Container Apps certificate requires DigiCert to reach app ingress for validation and automatic renewal. A direct CNAME alone does not meet that requirement. If the root already has CAA records, a DigiCert authorization is also required for the Azure-managed option. Keep the single-operator allowlist. For a private branded URL, use an existing certificate in the Container Apps environment. A certificate issued through ACME DNS-01 can validate ownership through DNS while ingress stays restricted. Assign a renewal owner, monitor expiry and rehearse rebind and rollback before adopting it. No managed certificate, DNS change, domain purchase or new service was authorized by this preparation. ## Bind the approved hostname

1. The owner confirms the exact name, checks the price and registers it with the chosen registrar. Use the DNS zone under the owner's control. Leave the apex free for the showcase.
2. Read the generated FQDN and custom-domain verification value from the existing app's Custom domains blade. Publish the following records in the approved root zone. Some providers append the zone automatically.

   | Type | Relative name | Value |
   | --- | --- | --- |
   | CNAME | `demo` | The generated `ca-etaye-demo.…azurecontainerapps.io` FQDN |
   | TXT | `asuid.demo` | The Azure app's exact Custom Domain Verification ID |
   | TXT | `_acme-challenge.demo` | The one-time DNS-01 challenge from the certificate issuer, if used |

3. Obtain the SNI certificate for `demo.<approved-domain>` with its full chain. In the existing `cae-etaye-demo` environment, use Certificates → Bring your own certificates → Add. Keep the cert file and private key in the operator's private store. Record the resulting Azure certificate resource ID and expiry in the private deployment evidence. Reuse that resource ID in the binding. Use one owner to manage the app binding through Bicep.
4. Set `customDemoDomain.hostname` and `customDemoDomain.certificateId` in the reviewed secure Bicep parameters. Retain both parameters on later Bicep rollouts that should preserve the binding. Leave the ingress HTTPS-only with the exact approved rule. Verify DNS from the public resolver and compare the validation TXT privately. During activation verify certificate name, chain and expiry on the alias, then use its own `/connexion` and same-origin `/api/v1/session`. Apply the acceptance matrix to the alias and generated hostname.

## Private rollout and rollback

**To verify before promotion.** The target image and database must match an attested release that passed restricted staging. The live database was recorded at V11 with fixture generation 1. Current published main requires later migrations. [Protected staging preparation](https://github.com/Aymenchaghoub/etaye/pull/107) is separate and must establish database compatibility and candidate acceptance before any image or traffic change. Keep the Azure runtime on the last verified release while this is pending. If it is already in Multiple revision mode at rollout, use the [protected staging procedure](cloud-demo-runbook.md#runtime-release-and-continuous-delivery) to preserve exact mode, pinned traffic and ingress. The current staging workflow stages image digests. A later configuration-only revision needs a reviewed operator change that preserves that traffic pin. The app Bicep declares Single mode. Applying it directly to a pinned Multiple deployment would change revision handling.

1. Save the current secret references, ingress settings, complete active revision name, immutable image digests and compatible database version privately. Verify that `demo-operator` is the only rule, with the approved `/32`, and that no extra ports or public links are active. Record an allowed-network positive request and an independent non-allowlisted negative request against the generated hostname. Use network sources you control. Keep the allowlist in place.
2. Release and test the edge image in Basic mode first. Confirm Nginx routes, private readiness, external authenticated reads and browser boundaries. Once the release is verified and the intended revision can be activated safely, set `edgeAuthMode=ip-restricted` with the same immutable images and same ingress rules. For a Bicep configuration-only revision in Single mode, set a fresh `revisionTag` of lowercase letters, digits and single dashes, starting with a letter and ending with a letter or digit. Run provider what-if with private parameters and inspect the diff before applying. Stop if it changes IP scope, additional ports, secrets, replica limits, revision mode or database. Prefer removing Basic on the generated host before bundling a DNS change.
3. Check the following from both hosts once an alias exists. From the allowed IP, HTTP redirects to HTTPS, TLS validates, `/connexion` loads directly, headers include CSP, frame protection, no-store and noindex, and unauthenticated protected API calls return `401` without Basic. From the independent disallowed IP, Azure blocks access to the root and protected API before Nginx, including the generated and any active revision or label hostname. Confirm a valid session, invalid-login handling, a CSRF rejection and secure cookie attributes. With synthetic practitioner, patient and administrator accounts, check same-practice reads, cross-practice denials and administrative ownership. Verify clinical writes, the reset, invitation and recovery remain closed. Verify platform probes and inspect the actual replica and database usage.
4. If a check fails, pause external traffic with the [existing operator procedure](cloud-demo-runbook.md#inspect-pause-and-resume-the-demo). Under the same allowlist, restore `edgeAuthMode=basic` in a new configuration revision using the same compatible images and visitor hash, or reactivate the pinned last-known-good compatible revision when available. If the binding caused the issue, restore the previous app ingress binding and exact origins, and separately revert the DNS changes if approved. Cloud database migrations are forward-only. Verify readiness, the Basic challenge on available hosts, successful permitted sign-in and denial from the disallowed network before resuming. Save sanitized evidence outside Git.

### Verify an unpromoted revision

**Verified observation.** Azure returns a distinct HTTPS FQDN from the revision resource. On the live Single-mode app, an approved-network request to that address returned `421` before Basic because the Nginx host guard only recognizes the app's generated hostname. The ordinary image-only staging action keeps that guard. A ready revision and a successful request to the traffic-pinned app hostname alone therefore do not prove the candidate passed browser acceptance.

**Proposed procedure for the first private rollout, before a branded domain exists.** After the authorized image-only stage, retain the known-good 100% traffic pin and operator IP rule. Copy the signed candidate's template into a configuration-only review revision, with a fresh suffix and the same digests. Set the Web container's `ETAYE_CUSTOM_INGRESS_HOST` to that review revision's exact generated FQDN, and append that exact `https://` origin to the API container's `ETAYE_WEB_ALLOWED_ORIGINS`. Keep `ETAYE_EDGE_AUTH_MODE=basic` for the first campaign. The Azure revision FQDN follows `<full-revision-name>.<app-environment-suffix>` on the current app. Confirm the computed value against `az containerapp revision show --query properties.fqdn` after configuration. Use the existing Azure hostname and certificate for this test, with no custom domain binding, DNS edit or wildcard host. Inspect the candidate template and ingress before dispatching the protected operator change, then test the exact review URL from allowed and disallowed sources while the serving traffic remains pinned.

For an IP-only review revision use its own exact FQDN, keep the same IP rule and repeat the signed-in and unauthenticated checks. Remove the temporary review hostname from the next configuration when it is no longer needed. A branded alias occupies the regular second hostname slot. Once that alias is live, revise the candidate review approach before changing a configured alias or its exact browser origin. The restricted multi-revision campaign and the configuration changes remain pending live approval and testing. ## Prerequisites for any public portfolio rollout

| Item | Current evidence and remaining work |
| --- | --- |
| Data and presentation | The cloud root identifies the synthetic demonstration in French. Before public access, review seeds, binaries, logs and backups for synthetic-only content. Keep the public showcase separate from signed-in record access and omit internal operational text. |
| Accounts and permissions | Keep practitioner and patient journeys bounded by server-side roles and practice/record ownership. Keep administrator and operator credentials private. Repeat real permission and isolation checks against each proposed public role. [Practice isolation ADR](../decisions/ADR-003-practice-isolation.md) |
| Abuse and load | Existing account/session budgets protect selected operations. The proxy strips client-supplied forwarding headers. Measure limiter behavior under shared proxy source addresses and avoid assuming independent per-visitor buckets. Assess request and login limits, account sharing, automation, concurrent sessions and response to quota exhaustion using synthetic traffic before public rollout. |
| AI and mail | The cloud fixture uses no external AI or email. Keep both disabled for public viewing. Any future generation needs reviewed per-actor and aggregate quotas, bounded jobs and spend alerts with a tested stop procedure. |
| State and reset | Cloud writes and the fixture reset are blocked at ingress. Keep a bounded operator-only reseed and recovery workflow. Public editable state would need an approved isolation and reset design. Rehearse session invalidation and test concurrent use before allowing any shared mutations. |
| Environment and secrets | Continue using the separate demo Azure app, database and non-owner roles. Verify that development, CI, recovery, inbox, infrastructure credentials and privileged routes cannot be exposed by the demo. Decide explicitly whether the existing authenticated public Neon endpoint is acceptable for the synthetic public demo. |
| Cost | Keep the existing budget and scale-to-zero profile. Measure cold start, request volume, Azure diagnostics and Neon resource usage without constant health polling. Set release thresholds for consumption and a named owner with a tested pause route. |

**Proposal.** Start with a public showcase and a short practitioner and patient walkthrough using read-only examples. Put the interactive routes after Étaye sign-in and use limited synthetic accounts. Validate the experience and costs first. Public exposure, an IP policy change, shared credentials or a new product entry route each need a separate decision.
