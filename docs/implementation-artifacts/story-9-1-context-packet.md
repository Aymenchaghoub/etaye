## 2. Requirements, boundaries and existing behavior

- **FR-019** owns the capability: coherent fictional data only, honest reset and unavailable states. **BR-018** owns the invariants: only the shared fictional dataset; at least two isolated practices demonstrate positive and negative authorization; public visitors cannot submit real patient data, trigger unbounded provider calls or access operational secrets; demo reset is isolated, rate-limited, returns to a known fixture version without silently corrupting other active sessions; reset/session-expiration notices are shown; deterministic AI exercises the external-provider boundary; unavailable states preserve entered work where safe, never claim false success. **J-08** owns the observable order: fictional-data notice → choose actor → complete journey → controlled reset/version notice; reset invalidates stale contexts without mixing old/new fixture IDs.
- **Access matrix.** The unauthenticated visitor's capabilities are "public showcase, synthetic demo entry, login/recovery requests" with no practice, patient or membership enumeration. The portfolio operator holds "synthetic demo reset and service operations" and no routine clinical browsing. The operator is an operational access, not a product role.
- **Existing application (verified at the baseline).** The API serves readiness, CSRF, meta, session/sign-in/recovery, invitation activation and the two patient carrier operations; modules are `identity`, `practices`, `records`, `audit`, `communications`, `infrastructure`. No demo module, no `/demo/*` route, no fixture seeding and no seeded demo accounts exist yet; the 10.1 test fixtures are explicitly test-only and are not the demo dataset. The web app is the account/auth shell with `/compte`, `/compte/pratiques/{membershipId}` and `/compte/patient/{portalLinkId}` routes. `ETAYE_DEMO_RECOVERY_INBOX=true` already demonstrates the local mail-sink pattern this story's package can reuse.
- **Demo dataset.** [synthetic-data.md](../design/synthetic-data.md)/[json](../design/synthetic-data.json) (`etaye-design-v1`, baseline Monday 2 November 2026 16:00 Europe/Paris) owns the cast (PRA-A/PRA-B, PR-NORA, PR-SAMI-A/B, PR-ELODIE, ACC-MILA, R-A-001/002/003, R-B-001, invitation fixtures), the narrative and the variation overrides (`V-EMPTY`, `V-AI-DOWN`, …). Readable IDs are design aliases; a future fixture adapter maps them to deterministic UUIDs (contract README "Examples and design aliases"). Runtime seeds regenerate relative dates where the narrative requires it (invitation precedent, 2026-11-21).
- **Related decisions.** UD-21 fixed seeded slot grid; UD-24 demo files in PostgreSQL or a persistent volume behind the FileStore port; UD-25 €0 first (the public hosting itself belongs to 10.3); UD-30 deterministic brief composer (the demo needs no paid model); D-35 anonymous CSRF/session issuance is unbounded and must be bounded before the API is reachable outside a local machine — the 9.1 package runs locally, so 9.1 does not fire D-35's trigger, but the demo entry is precisely the anonymous path that will.
- **Out of scope, owned elsewhere:** the fuller in-journey recovery of S-37/S-38 and I-22/I-23 (9.3), release quality evidence (9.2), the hosting benchmark and public deployment (10.3), invitation issuance and resend flows (D-23), practice settings (D-21), audit and profile screens (D-30/D-31), scheduled reset cadence (**[Proposal]** manual operator reset only in 9.1; a disclosed cadence is proposed by security/privacy for later — **To verify** whether any reusable job facility exists at that time), the guided "Prouvez l'isolation" journey artifact (1.4/UD-33, although S-01 shows its entry point per DF-18).

## 5. Data, authorization and reset boundaries

- **Demo dataset seeding.** A demo fixture loader owns `etaye-design-v1` → deterministic UUID mapping (contract README), both practices, the cast, the narrative rows and the invitation fixtures; the loader runs from the demo package (compose) and from test tooling. Test fixtures and the public demo dataset stay separate (architecture spine: "a test never points at the public demo database"). Demo credentials are synthetic and non-secret; they never appear in audit/log bodies (BR-017 keeps credentials out of logs).
- **Reset mechanics.** The data model allows hard delete only for "a documented demo reset/retention operation with referential ordering; no broad cascading deletion of clinical evidence". **Proposal:** reset = drop/recreate demo schema content or restore the seeded snapshot in referential order inside one bounded job (AD-8: leased, single-writer, only the current lease commits), then close the sessions and publish the new fixture generation through the E1 field. Rate-limit per operator (429 declared). A reset during in-flight journeys must not mix old/new fixture IDs (J-08): close sessions first or version-stamp requests so late writes fail closed.
- **Isolation.** `/demo/*` routes are not practice-scoped; they must not establish any practice context or clinical grant. BR-018 requires two isolated practices in the demo: the seeded PRA-A/PRA-B data carries that structure, and the denial demonstrations are exercised interactively by 1.4's journey (UD-33); 9.1 presents the fictional context honestly and must not claim clinical validation or real-care readiness anywhere in the public copy or README.
- **Anonymous path.** `/demo/scenarios` is anonymous like `/csrf`; D-35's unbounded anonymous-session growth applies the moment the API is reachable beyond localhost. The 9.1 package is local, so 9.1 documents the dependency and 10.3 (public hosting) fires the trigger.
