## 2. What exists today (verified in the baseline)

- **`createPatient` already runs.** Story 10.1 delivered it as a carrier: `PatientController` (`CLINICAL_WRITE`, `Idempotency-Key` 16–128 characters), `PatientService` (advisory lock per key, canonical body hash, receipt replay, `Patient` + empty `PatientRecord` + `PATIENT_CREATED` audit + outbox row + receipt in one practice transaction) and the strict `PatientEdit` validation (required names and birth date, birth date not in the future, strict `YYYY-MM-DD`, email format, phone ≤ 40). It has **no duplicate detection** and no `PATIENT_REGISTER` or `SCHEDULE_MANAGE` path. `getPatientRecord` (`CLINICAL_READ`, ETag, 304) also exists. `searchPatients`, `editPatient`, `searchSchedulingPatients` and `registerSchedulingPatient` do not exist in `apps/api`; the generated web SDK already contains their stubs from the contract.
- **Schema.** `patient` (first/last name, birth date, nullable email and phone, `version`) and `patient_record` (unique per patient, `record_revision`) with forced RLS. The runtime role has **`SELECT, INSERT` only** on both tables (V1). `PATIENT_REGISTER` is already an allowed capability value in the membership and invitation checks. Migrations V1–V4 and V7 are in `db/migration`; V5 and V6 belong to the local demo package under `db/demo`. The next migration number is V8 (**To verify** against the Flyway locations before writing it).
