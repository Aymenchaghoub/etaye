## 1. Objective and gates

An authenticated account holder with multiple memberships or verified patient links can select and switch to one work context. The destination identifies the current practice and working role. Prior-practice screens, caches, draft state and links leave the active view at the switch boundary. A stale or unauthorized selection exposes no protected data.

## 2. Requirements, boundaries and existing behavior

- **FR-002, BR-001–003, J-01** require a globally authenticated account, one explicit practice context per active view, current grants, capability and resource ownership on each protected request. A membership suspension removes that context while unrelated grants can remain usable. An administrator has operational permissions and needs an explicit clinical grant for clinical access. An account with zero eligible contexts reaches a safe empty state.
- **FR-016, BR-002/004** require an active, verified self-link to the exact practice-local record for patient access. Two links to the same practice can mean different record contexts. A staff grant and a portal link to the same practice are separate contexts. Neither email nor a practice ID resolves a patient record. J-06 explains the later portal journey and audience constraints.
- **BR-015 and SP-SAVE** apply to I-20. Stay keeps input in its original authorized context. Discard requires an explicit choice. Save and continue waits for confirmed persistence under the original context's permission and version guards. Expiry uses the 1.2 flow. If the source grant is lost, remove the protected view and its local state. **BR-017 / UD-47** govern denial audit when an actor practice is established. Keep the response generic if auditing fails.
- **User decisions.** A-01 is confirmed by UD-19, A-02/A-04/A-05 are the UD-37 working baselines, and A-03 is confirmed by UD-20. A-06 through A-12 provide no additional AT-003 gate. Portal publications, the full isolation demonstration, feature editors, team administration, native and offline data retain their story ownership. D-08/D-09/D-17/D-19/D-23 keep delegation, record exchange, offline clinical storage, native session duration and invitation issuance deferred. D-36 and D-41 retain the account lifecycle and carrier lock-wait follow-ups. Avoid attaching the existing create-patient mutation to I-20 as a substitute for a scoped editor.
- **Verified observation.** The 1.2 Web entry uses `/compte`, `/compte/pratiques/{membershipId}` and `/compte/patient/{portalLinkId}`. `AccountGate` checks `getSession` on entry, while visible, on visibility return and on `pageshow`. Its current destination is a protected account view. Paused work is scoped to account and exact allowed path. 1.1 now returns a session after invitation acceptance and can route directly to the just-activated portal link. Preserve those entry points and test stale/denied return, reconnect, logout and account change.
- **User decision (UD-52).** Use the existing account and scoped routes with a minimal destination that shows practice, audience/role and an accessible switch action. Keep selection local to the tab and route. Validate the target with fresh account-scoped resolution before showing it. A legitimate deep link must be resolved as a new guarded entry. A stale or incompatible link routes to safe recovery without displaying another context or transplanting the old resource ID into the new path. Keep a first-class practice/record check at every protected API boundary.

## 5. Data, authorization and transition boundaries

- **Verified observation.** V1 defines practice/account/membership and the record carrier. V2 defines a verified `portal_link` with composite practice/record ownership and provides `current_session_grants`. V3 integrates invitation activation. The restricted identity lookup resolves the actor in transaction-local account context. Its current grants return IDs/types for active grants in active practices. Membership data has practice/capability scope, and session responses expose grant IDs only.
- **Proposal.** Extend the restricted own-account lookup for context metadata as required by the chosen contract, with active account/grant/practice checks and least privilege. Any SQL function/view change uses a forward Flyway migration and clean plus V3-upgrade evidence. Existing practice-owned resource operations continue through the current nonowner/non-bypass runtime and transaction-local `practice_id` on the same connection. Verify the separate portal record constraint and current capability checks. A tab context is navigation state and supplies no authority. Use no persistent cookie/session preference for the active practice in this slice.
- **User decision (UD-52).** On switch, settle I-20 if needed, revalidate the target, block rendering across the transition, cancel pending reads and reject late responses for the old account/grant/transition. Clear previous record queries, search/filter results, drafts, links, open panels and resource navigation before rendering the destination. Reset on sign out, session/account mismatch, confirmed revocation and stale browser restoration. Do not persist protected data in Web Storage, IndexedDB or a service worker. Re-enter through a fresh authorization check on history or back-forward cache restoration. Multi-tab use keeps explicit practice-qualified requests and never retargets another tab's in-flight writes.
- **Accepted behavior (UD-52).** If save commits and target revalidation fails, report that the source save succeeded, keep the switch uncommitted and recheck whether the source can still be shown. On a lost save response, recover the outcome according to the owning operation's contract before permitting retry. A failed destination must never imply safe persistence. On an outage while checking access, show an honest unavailable state and retry with fresh grants. If a draft is eligible for recovery, keep it in memory bound to the same account, grant and resource; never transfer it to the target.
